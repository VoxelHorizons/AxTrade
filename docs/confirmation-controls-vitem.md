# Confirmation controls and VoxelCore items

## Confirmation item rendering

The **own** and **partner** confirmation controls default to a single item
throughout the trade, including the 5-second (or custom) confirmation window.
The legacy global setting `static-accept-item-amount` has been retired; its
stored value in `config.yml` is ignored.

Set `use-confirm-countdown: true` directly on a `confirm-item` or
`confirm-item-pad` section to display remaining seconds as stack quantity
*after that side has confirmed*. Both sides are independent. An explicit
`amount` in the YAML is honored when countdowns are disabled; otherwise the
default is one item. Countdown quantities are clamped to 1–64.

Confirmation item **names and lore are never generated by the trade state**.
The actual `accept` or `cancel` definition determines the item metadata;
a `name` or `lore` field directly under `confirm-item` is inherited in
both states unless the state explicitly overrides it:

```yaml
own:
  confirm-item:
    slot: 9
    use-confirm-countdown: false
    name: '&aMy trade confirmation'
    lore:
      - '&7Always the same description in both states'
    accept:
      material: RED_CONCRETE
    cancel:
      material: LIME_CONCRETE

partner:
  confirm-item:
    slot: 14
    use-confirm-countdown: false
    name: '&fPartner confirmation'
    lore:
      - '&7Read-only view'
    accept:
      material: RED_CONCRETE
    cancel:
      material: LIME_CONCRETE
```

For state-specific text, define `name` and/or `lore` inside `accept` and
`cancel`; those fields override the shared defaults *only for that state*.
The same rules apply to padding controls. Configured colors, placeholders,
glyphs, item model data, and textures are preserved.

## `vitem`: registered VoxelCore items and resource-pack assets

`vitem` is a new, **optional** rendering source in any GUI item section
(including heads, decorative items, currency buttons, confirmation items and
pads). It is processed through AxTrade's existing VoxelCore bridge, without
a compile-time dependency.

```yaml
own:
  confirm-item:
    slot: 9
    accept:
      vitem: 'voxel:ui-blank'
      material: RED_CONCRETE  # fallback if VoxelCore is unavailable or ID fails
      name: '&aConfirm Trade'
      lore: ['&7Click to accept']
    cancel:
      vitem: 'voxel:ui/blank'
      material: LIME_CONCRETE # fallback when VoxelCore is unavailable
      name: '&eCancel Confirmation'
```

- `vitem: voxel:ui-blank` loads a *registered VoxelCore item* via
  `ItemManager.createItem`; abstract display-only definitions use
  `createRenderItem`. It preserves the returned item material, PDC,
  item-model and other metadata. Only explicitly configured AxTrade fields
  such as `name`, `lore`, `texture`, or `amount` replace that metadata.
- `vitem: voxel:ui/blank` (slash path) denotes a *raw item-model asset*,
  not a registered item. It sets Minecraft's item-model component to
  `voxel:ui/blank`, using `PAPER` as the carrier unless a valid fallback
  `material` is configured. The final resource pack **must contain**
  `assets/voxel/items/ui/blank.json` (or an equivalent item-model definition).
  A plain PNG or model geometry file by itself is **not enough**.
- If VoxelCore is missing, a configured vanilla `material` is used. If
  neither VoxelCore nor a fallback material is available, a visible `BARRIER`
  is used instead of silently putting air in the GUI.
- Existing `voxelcore: voxel:id`, `material: voxel:id`, and vanilla
  `material: RED_CONCRETE` configurations continue working. `vitem`
  takes precedence when multiple item sources are configured.
- `vitem` and its optional fallback are evaluated **at item-render time**.
  Disabling/uninstalling VoxelCore does not prevent AxTrade from starting.

### Test matrix

1. Confirm both sides default to one red/green stack when countdown starts,
   despite legacy `static-accept-item-amount: false`.
2. Put shared name/lore in the parent and different colors in
   `accept`/`cancel`; verify text remains unchanged across state changes.
3. Put state-specific name/lore in `accept` and `cancel`; verify each
   configured variant displays accurately with PAPI/VoxelCore aliases.
4. Enable `use-confirm-countdown` only for the partner pad, then test the
   countdown without changing the main confirmation controls.
5. Test `vitem` with a registered item, an abstract display item, and a
   packaged raw item-model asset, including custom name and lore overrides.
6. Disable VoxelCore and confirm vanilla `material` fallbacks work, and that
   changing confirmation controls/currency values does not lose offered items.

Note: PR #3 separately corrects the initial rendering of `own.head` and
`partner.head`; this change does not replace that fix.
